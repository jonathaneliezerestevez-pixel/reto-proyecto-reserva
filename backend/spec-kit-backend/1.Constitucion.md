# Constitución del Backend

## 1. Propósito

Este documento define la constitución técnica del backend para el sistema de reservas de mesas del restaurante. El backend expondrá una API REST para administrar la autenticación del administrador y las reservas almacenadas en la base de datos `reservadb`.

## 2. Tecnologías principales

| Área | Tecnología | Decisión |
|---|---|---|
| Lenguaje | TypeScript | Tipado estático, mejor mantenibilidad y detección temprana de errores. |
| Capa HTTP | HonoJS | Framework ligero, basado en Web Standards y compatible con Vercel. |
| Autenticación | JWT | Autenticación mediante tokens firmados para las rutas protegidas. |
| Contraseñas | bcrypt/bcryptjs | Hash irreversible de contraseñas con 8 salt rounds. |
| Validación | Zod | Validación y tipado de cuerpos, parámetros y filtros. |
| Base de datos | PostgreSQL | Utilizará la base `reservadb` y las tablas `Administrador`, `Reserva` y `Restaurante`. |
| Despliegue | Vercel | Ejecución del backend como funciones serverless. |

## 3. Arquitectura

Se utilizará una arquitectura de **tres capas**, preferible a un MVC tradicional para este backend REST. MVC puede aplicarse dentro de la capa de presentación, pero la separación adicional de servicios y persistencia facilita las pruebas y el mantenimiento.

```text
backend/
├── src/
│   ├── app.ts
│   ├── routes/
│   ├── controllers/
│   ├── services/
│   ├── repositories/
│   ├── schemas/
│   ├── middleware/
│   ├── config/
│   ├── types/
│   └── utils/
├── tests/
├── package.json
├── tsconfig.json
└── vercel.json
```

### 3.1. Capa de presentación

Responsabilidades:

- Definir las rutas HTTP con HonoJS.
- Recibir solicitudes y devolver respuestas JSON.
- Ejecutar validaciones de entrada con Zod.
- Aplicar middleware de autenticación, CORS, logging y manejo de errores.
- No contener reglas de negocio ni consultas SQL directamente.

Componentes principales:

- `routes/`: definición de endpoints.
- `controllers/`: adaptación entre HTTP y los servicios.
- `middleware/`: autenticación JWT, errores y seguridad.
- `schemas/`: esquemas Zod.

### 3.2. Capa de aplicación o dominio

Responsabilidades:

- Contener las reglas de negocio.
- Coordinar autenticación y operaciones de reservas.
- No depender de detalles HTTP.

Componentes principales:

- `services/auth.service.ts`.
- `services/reserva.service.ts`.

### 3.3. Capa de infraestructura

Responsabilidades:

- Gestionar la conexión con PostgreSQL.
- Ejecutar consultas parametrizadas.
- Implementar los repositorios utilizados por los servicios.
- Gestionar configuración y variables de entorno.

Componentes principales:

- `repositories/administrador.repository.ts`.
- `repositories/reserva.repository.ts`.
- `config/database.ts`.

## 4. Dependencias del backend

### Dependencias de ejecución

- `hono`: framework HTTP.
- `zod`: validación y definición de esquemas.
- `@hono/zod-validator`: integración de Zod con Hono.
- `jose`: creación y verificación de JWT usando Web Standards, adecuada para Vercel.
- `bcryptjs`: hashing de contraseñas sin dependencia nativa, conveniente para funciones serverless. Se configurará con 8 salt rounds.
- `pg` y `@types/pg` para la conexión con PostgreSQL.

### Dependencias de desarrollo

- `typescript`.
- `tsx`.
- `vitest`.
- `eslint`.
- `prettier`.
- Tipos de Node.js cuando sean necesarios por el runtime elegido.

> Si se requiere específicamente el paquete nativo `bcrypt`, se debe verificar la compatibilidad del binario con el runtime de Vercel. Como opción predeterminada se utilizará `bcryptjs` para evitar problemas de compilación en despliegues serverless.

## 5. Modelo de datos

La conexión PostgreSQL se configurará mediante `DATABASE_URL` con formato `postgresql://usuario:contraseña@host:puerto/base`. Para Supabase se debe configurar `DATABASE_SSL=true` y utilizar la cadena oficial del botón **Connect**.

### Administrador

- `Identificador`.
- `Usuario`.
- `Contrasena`.

La contraseña almacenada por el backend deberá ser un hash bcrypt. El valor inicial definido en el script SQL deberá migrarse a un hash antes de utilizar autenticación en producción.

### Reserva

- `Identificador`.
- `NombreCliente`.
- `NumeroCliente`.
- `EstadoPedido`.
- `NumeroMesa`.
- `FechaReserva`.

### Restaurante

El sistema incluye un restaurante demo editable desde el panel administrativo. Sus datos públicos se almacenan en `Restaurante`:

- `Nombre`.
- `Descripcion`.
- `TipoComida`.
- `Direccion`.
- `Zona`.
- `Telefono`.
- `TelefonoReservas`.
- `Correo`.
- `HorarioAtencion`.
- `RedesSociales`.
- `SitioWeb`.
- `LogoUrl`.
- `FotografiasReferencia`.
- `RangoPrecios`.
- `PlatosPrincipales`.
- `EsDemo`.

`RedesSociales` y `FotografiasReferencia` se almacenan como JSON. Las fotografías y el logo se mantienen vacíos cuando no existe autorización de uso.

Las reservas nuevas se asocian con `RestauranteId`. Las reservas existentes se conservan y la migración las vincula al restaurante demo cuando no tienen asociación.

Los estados permitidos son `Disponible` y `Cancelado`.

## 6. Requerimientos funcionales

### RF-01. Inicio de sesión del administrador

- Recibir usuario y contraseña.
- Validar los datos con Zod.
- Buscar el administrador por usuario.
- Comparar la contraseña con bcrypt.
- Generar un JWT firmado si las credenciales son correctas.
- Devolver una respuesta de autenticación sin exponer la contraseña.

### RF-02. Cierre de sesión del administrador

- El cliente deberá eliminar el token o la cookie de sesión.
- Si se requiere invalidación inmediata antes del vencimiento del JWT, se implementará una lista de revocación persistida.
- La estrategia inicial será JWT de corta duración y eliminación de la sesión en el cliente.

### RF-03. Registrar una reserva

- Validar los datos de la reserva.
- Permitir los estados `Disponible` y `Cancelado`.
- Usar la fecha actual por defecto cuando no se proporcione `FechaReserva`.
- Requerir autenticación del administrador.

### RF-04. Actualizar una reserva

- Recibir el identificador de la reserva.
- Validar únicamente los campos permitidos.
- Verificar que la reserva exista.
- Requerir autenticación del administrador.

### RF-05. Listar reservas

- Devolver las reservas ordenadas por fecha de reserva.
- Requerir autenticación del administrador.

### RF-06. Listar reservas filtradas

Se permitirán filtros opcionales por:

- `EstadoPedido`.
- `FechaReserva`.
- `NumeroMesa`.
- `NombreCliente`.
- `NumeroCliente`.

Todos los filtros deberán validarse con Zod y utilizar consultas parametrizadas.

## 7. API REST propuesta

| Método | Endpoint | Descripción | Autenticación |
|---|---|---|---|
| `POST` | `/api/auth/login` | Iniciar sesión | No |
| `POST` | `/api/auth/logout` | Cerrar sesión | Sí |
| `POST` | `/api/reservas` | Registrar una reserva | Sí |
| `PUT` | `/api/reservas/:id` | Actualizar una reserva | Sí |
| `GET` | `/api/reservas` | Listar reservas | Sí |
| `GET` | `/api/reservas?estado=Disponible` | Listar reservas filtradas | Sí |
| `GET` | `/api/restaurante` | Consultar información pública del restaurante demo | No |
| `PUT` | `/api/restaurante` | Actualizar información del restaurante demo | Sí |

Las respuestas utilizarán JSON y una estructura consistente para datos, errores y mensajes.

## 8. Seguridad

- Nunca guardar contraseñas en texto plano.
- Utilizar bcrypt con 8 salt rounds.
- Firmar JWT con una clave almacenada en una variable de entorno.
- No incluir contraseñas ni secretos en respuestas o logs.
- Validar todas las entradas con Zod.
- Usar consultas parametrizadas para prevenir inyección SQL.
- Aplicar CORS únicamente a los orígenes autorizados.
- Configurar cookies `HttpOnly`, `Secure` y `SameSite` si el JWT se transporta mediante cookie.
- Configurar expiración corta para los tokens.
- Gestionar secretos exclusivamente mediante variables de entorno.

## 9. Variables de entorno

```env
DATABASE_URL=
JWT_SECRET=
JWT_EXPIRES_IN=15m
COOKIE_NAME=admin_session
ALLOWED_ORIGINS=http://localhost:4321,https://nookis3.infosist.org
NODE_ENV=development
```

No se deberán incluir valores reales en el repositorio.

## 10. Compatibilidad con Vercel y Hono

Hono dispone de soporte oficial para Vercel y puede desplegarse con configuración mínima o cero configuración. La aplicación deberá exportar la instancia de Hono como `default` desde uno de los archivos reconocidos por Vercel, preferiblemente:

```text
src/index.ts
```

Ejemplo de entrada:

```ts
import { Hono } from 'hono';

const app = new Hono();

export default app;
```

Para desarrollo y despliegue se utilizarán:

```bash
vc dev
vc deploy
```

Consideraciones:

- Cada ruta se ejecutará como función serverless de Vercel.
- No se almacenará estado de sesión en memoria.
- Las conexiones a la base de datos deberán ser compatibles con serverless y reutilizarse cuando sea posible.
- Las variables de entorno se configurarán en Vercel.
- Se utilizará `jose` por su compatibilidad con Web Standards.
- Los archivos estáticos, si fueran necesarios, se ubicarán en `public/`.
- No se dependerá de un servidor HTTP persistente ni de `serveStatic()` para el despliegue en Vercel.

Documentación oficial:

- [Hono en Vercel](https://hono.dev/docs/getting-started/vercel)
- [Hono en Vercel Docs](https://vercel.com/docs/frameworks/backend/hono)

## 11. Fases de construcción

### Fase 1. Constitución e inicialización

- Crear el proyecto TypeScript.
- Instalar HonoJS y las dependencias base.
- Configurar `tsconfig.json`, scripts y linting.
- Crear la estructura de directorios.
- Configurar variables de entorno.

### Fase 2. Configuración de infraestructura

- Configurar la conexión PostgreSQL.
- Implementar el repositorio de administradores.
- Implementar el repositorio de reservas.
- Verificar la conexión con `reservadb`.
- Crear manejo de errores de persistencia.

### Fase 3. Validaciones y contratos

- Crear esquemas Zod para login.
- Crear esquemas para registrar y actualizar reservas.
- Crear esquemas para filtros.
- Definir tipos de entrada y salida.
- Estandarizar respuestas y errores.

### Fase 4. Autenticación y autorización

- Implementar comparación con bcrypt.
- Implementar generación y verificación de JWT.
- Crear middleware de autenticación.
- Implementar login y logout.
- Proteger los endpoints de reservas.

### Fase 5. Gestión de reservas

- Implementar registro de reservas.
- Implementar actualización de reservas.
- Implementar listado general.
- Implementar filtros.
- Aplicar reglas de estados y fechas.

### Fase 6. Pruebas

- Probar login válido e inválido.
- Probar acceso con token ausente, inválido y expirado.
- Probar logout.
- Probar creación y actualización de reservas.
- Probar filtros.
- Probar validaciones y errores de base de datos.

### Fase 7. Preparación para Vercel

- Confirmar exportación `default` de la aplicación Hono.
- Configurar variables de entorno en Vercel.
- Verificar el driver y el límite de conexiones de la base de datos.
- Ejecutar pruebas con `vc dev`.
- Realizar el despliegue con `vc deploy`.
- Validar endpoints en el entorno de producción.

## 12. Criterios de aceptación

- El administrador puede iniciar sesión con credenciales válidas.
- Las contraseñas no se almacenan ni se devuelven en texto plano.
- Las rutas de reservas exigen un JWT válido.
- Se pueden registrar y actualizar reservas.
- Se pueden listar reservas completas y filtradas.
- Los estados inválidos son rechazados.
- Las entradas inválidas producen respuestas `400` claras.
- Los recursos inexistentes producen respuestas `404`.
- Los errores no controlados producen respuestas `500` sin exponer información sensible.
- El backend puede ejecutarse localmente y desplegarse en Vercel.
